# Memory Bank

## Learned Patterns & Decisions

### Code Style
- C++ mit sol2-basierter Lua API, Zielplattformen: Windows, Mac, Linux.
- Domain: Echtzeit-3D-Engine für Tomb Raider-ähnliche Spiele.
-格子: Grid-based, room-based world structure mit Portalen.
- World units: 1 sector = 1024 world units ≈ 2 Meter.
- C-style casts bevorzugen (`(int)` statt `static_cast<int>`).
- Keine `_t` Typen im lokalen Code (z.B. `size_t`, `uint32_t`). Explizite Typen bevorzugen (`int`, `bool`, `float`).
- Floating-point numbers immer mit `f` postfix und Dezimalpunkt (z.B. `2.0f`).
- Namespace: keine anonymous namespaces.
- Includes: eigene `.h` → externe System-Includes → lokale Projekt-Includes (alphabetisch sortiert, gruppiert).
- Indentation: 4 spaces. Windows line endings.
- PascalCase für öffentliche Typen/Methoden. camelCase mit führendem `_` für private fields.
- `auto` bevorzugen wenn der Typ offensichtlich ist.
- One-line lambdas können zusammengefasst werden wenn sie ähnlich sind.
- **PropertyHandler Vektor-Property (wichtig):** Der Fallback-Default bei `PropertyHandler::Get(item, "Name", default)` bestimmt den Template-Typ `T`. `T` MUSS ein Mitglied der `PropertyValue`-Variante sein (`PropertyValue = std::variant<bool, float, std::string, Vec2, Vec3, ScriptColor, Rotation, Time>`, PropertyValue.h:16), sonst bricht `ExtractValue<T>` an `std::get_if<T>` (static_assert "T to occur exactly once in Types", C2338 — Fehler zeigt fälschlich auf MSVC `<variant>`). **Vektor → TEN `Vec2`/`Vec3`, NICHT DirectX `Vector2`/`Vector3`.** Korrekt: `Vector3 moveTargetPos = (Vector3)PropertyHandler::Get(*item, "GunshipMoveTarget", Vec3());` (`Vec3` → `Vector3` via `operator Vector3() const`). Integral-Typen (außer `bool`) werden aus dem gespeicherten `float` gelesen, Default darf z.B. `-1` sein.

### Tooling (PowerShell-File-Edits)
- **Expression-Arrays in PowerShell vermeiden:** `@( $a+$b+'x', $a+$b+'y' )` kollabiert zu EINEM Element (Elemente mit Leerzeichen getrennt, `@($arr).Count` = 1) → Multi-Line-Edits zerfallen zu einer Zeile. Für Array-Zeilen **Plain-Strings** `@("`t`tcode", "`t`tcode")` nutzen (` `t ` = Tab in Double-Quoted-Strings; `\t` wäre nur wörtlich). Vor `WriteAllLines` immer `@($arr).Count` verifizieren. Indentation zuverlässig mit `[char]9`-Kombination oder `` `t ``-Plain-Strings – NICHT mit `$t+$t+'...'`-Expressions in Arrays.

### Engine Architecture
- TombEngine implementiert klassische Lara-Croft-Physik (pre-TL1).
- Level-Dateien werden in einem eigenen Format verwaltet.
- Physik-System mit kollisionserkennung und character controller.
- Scripting über Lua mit sol2 — viele Skripte in `/Scripts/`.
- **LOS-Kette (Game/control/los.cpp):** `LOS()` = Geometrie (Wände/Collision-Mesh geschlossener Sektoren, Doors, Brücken, Portale via `GetRoomLosCollision`), klappt `target` auf den Wand-Treffer ab und füllt das GLOBALE `LosRoomNumbers`. `ObjectOnLOS2` = Items/Statics NUR – iteriert genau dieses `LosRoomNumbers`. **Regel:** `LOS()` muss IMMER vor `ObjectOnLOS2` laufen (Reihenfolge = `GetTargetOnLOS`); sonst wird eine stale Room-Liste des letzten Aufrufs genutzt → Durchschläge durch Wände möglich.
- **LOS-Strahl-Endpunkt NICHT in Boden/Geometrie begraben (wichtig, general):** `LOS()`/`GetRoomLosCollision` trace die Ray origin→target. Liegt der **Target-Punkt im Boden / innerhalb geschlossener Sektor-Geometrie**, trifft der Strahl den Boden/die Vorderkante **vor** dem Ziel → `IsIntersected=true` → falsches „blocked" (beobachtetes Symptom: Gunship FOLLOW/IDLE stand fälschlich still, obwohl die Sicht frei war). **Fix:** Test-Endpunkt ~0.5 Block über den Boden heben: `target += GameVector(0,-512,0,room)` (Y positiv = runter ⇒ **-Y = hoch**). Gleiche Sorgfalt für `origin` (Sichtpunkt nicht im eigenen Kollisionsvolumen; `people.cpp` setzt vor `GetLosCollision` `item.Collidable=false` gegen Selbst-Okklusion).
- **Gunship-LOS-Design (tr5_gunship.cpp):** Zustände trennen: `ESCAPE` = committed flight (vor-validiertes Ziel, Ausweich-Kaskade AUS), `EVADE_NEAR` = combat orbit (Kaskade AN, **einzige** Quelle des Auto-Escape), `FOLLOW`/`IDLE` = dynamisch. **Wichtig:** Neue LOS-/Wart-Logik darf `EVADE_NEAR` NICHT auf IDLE zwingen, sonst bricht der Auto-Escape-Pfad (der `blocked`-Block feuert `FindEscapeTarget` nur bei `blockedState == EVADE_NEAR`). **State-Schwellen:** `DetermineGunShipState` → `EVADE_NEAR < minDistance`, `IDLE ∈ [minDistance, maxShotsRange)`, `FOLLOW >= maxShotsRange`; „innerhalb Schussdistanz" = IDLE/EVADE_NEAR. **Teure per-Frame-Checks drosseln:** `GlobalCounter` (`extern int`, control.h) + `static`-Cache (Letzter-Test-Frame + Ergebnis), Intervall `FPS` (= 30). **LOS-Auswahl:** „keine Geometrie dazwischen" (Wand) → `LOS()` (Geometrie-Only, `true` = freie Sicht); NICHT `ObjectOnLOS2` (prüft Items → würde das Ziel selbst als „Treffer" melden).

### Coordinate System
- Y positiv ist downwards (im TEN-Koordinatensystem).
- **BoundingBox-Konvention (verifiziert):** `Y1 = Center − Extents` = OBERE KANTE (kleineres Y), `Y2 = Center + Extents` = UNTERE KANTE (grösseres Y). Beleg: `GameBoundingBox::Rotate` behandelt `(X1,Y1,Z1)` als min / `(X2,Y2,Z2)` als max; Aabb-Konstruktor `Y1 = center − extent`. Achtung: in `tr5_gunship.cpp` heisst `bottomMeshY (= pos.y + Y1)` faktisch TOP und `topMeshY (= pos.y + Y2)` BOTTOM (Namen vertauscht, Mathematik konsistent). `bandHeight = Y2 − Y1 > 0`.
- **NO_HEIGHT-Sentinel:** `NO_HEIGHT = INT_MIN + UCHAR_MAX`. `GetFloorHeight`/`GetCeilingHeight` liefern `NO_HEIGHT` (nicht `MAX_HEIGHT`!) wenn keine Fläche existiert → vor jeder Nutzung gegen `NO_HEIGHT` guarden; gültige Höhen sind immer ≥ 0.

## Key Files & Modules

### TR5 Gunship (`Objects/TR5/Entity/tr5_gunship.cpp`)
- State-Machine: `FOLLOW` / `IDLE` / `EVADE_NEAR` (enum `GunShipState`), Persistenz über `ItemFlags`.
- Vertikale Bewegung über persistenten `currentYSpeed` (`ItemFlags[6]`): geschrieben mit `* FLOATING_POINT_SCALE`, gelesen mit `/ FLOATING_POINT_SCALE`. Die Skala muss beidseitig stimmen, sonst bricht die Lerp-Akkumulation zusammen (früherer Bug: im EVADE-Zweig ohne `*1000` → Heli stieg nicht auf).
- **Y-Zielhöhe in ALLEN drei States:** `FOLLOW`, `IDLE` und `EVADE_NEAR` konvergieren alle auf `targetPos.y - OFFSET` (je `HOVER_HEIGHT_OFFSET` bzw. `EVADE_RAISE_HEIGHT`, beide 1.5 Sektoren). Der Heli überragt das Ziel dadurch immer, damit er nach unten zielen kann. WICHTIG: `FOLLOW` hatte ursprünglich KEINE Y-Verfolgung (nur `targetSpeed`) → Heli blieb auf alter Höhe, wenn Lara hinaufkletterte. Jetzt in allen drei Cases identisch.
- Logik-Prinzip Y-Verfolgung: `if (fabsf(posY - targetY) > minYDiff) ySpeed = (targetY > posY) ? FLY_DOWN_SPEED : -FLY_UP_SPEED;` (Y-down: größeres Y = tiefer; Ziel tiefer → runter, Ziel höher → rauf).
- `FixYPosition` clampt Boden-/Deckenabstand (Boden: `SECTOR_SIZE/4`, Decke: `SECTOR_SIZE/16`). Die Decke begrenzt den Aufstieg bei hohen Modellen – bei zu tiefer Mitte (unter dem Ziel) `minCeilingClearance` ggf. weiter senken.
- **Stabilität in Reichweite (wichtig):** `DetermineGunShipState` muss `horizontalDistance < maxShotsRange` → **immer** `IDLE` zurückgeben (unabhängig von `ItemFlags[7]`/`blockedEarly`). War IDLE an das Evade-Flag gekoppelt, lief der Heli in einem FOLLOW/EVADE-Loop an der `minDistance`-Grenze ("vorwärts ~1 s, Stopp, wieder vorwärts" — Rhythmik durch `inertiaTimer`-Reset + `currentSpeed = targetSpeed * pitchRatio`).
- **Evade-Flag (`ItemFlags[7]`):** nur Werte 0/1. `1` wird beim EVADE gesetzt und zurückgesetzt, sobald `dist > maxShotsRange && state != EVADE_NEAR`. Übergangsbedingungen an `yDiff` hängen lassen geht NICHT: die Y-Verfolgung hält den Heli auf `ZielY - 1.5 * SECTOR_SIZE`, daher sind kleine `|yDiff|`-Bedingungen nie erfüllbar (früherer Bug: `2 → 0` bei `|yDiff| < 0.5 * SECTOR_SIZE` → Flag lief nie zurück).
- **Pitch-Konvention (wichtig):** `Matrix`/`Vector3`/`Quaternion` = `DirectX::SimpleMath` (framework.h: `using namespace DirectX::SimpleMath`); `EulerAngles::ToDirection()` = `(sinY·cosX, -sinX, cosY·cosX)`. Heli-Pose-Yaw = Ziel-Yaw + 180°. Heckwaffe schießt entlang Modellachse `-Z` (Firing-Code nutzt `ToRotationMatrix` mit Pose-Pitch + 8°) → **Waffen-Abguerung ≈ Pose-Pitch + 8°**: positives Pitch = Nase OBEN = Waffe zielt nach UNTEN, negatives Pitch = Waffe zielt nach oben.
- **IDLE-Zielpitch:** `CalculateIdlePitch` = `atan2(0.25-Sektor-über-ZielPivot - HeliY, hDist) - 8°`, geclampt `[0, MAX_PITCH_DEG]` → Schüsse treffen um Laras Unterschenkel. WICHTIG dafür: (a) `UpdateIdleOrientation` nur bei `!= IDLE` aufrufen (setzt sonst ±MAX_PITCH), (b) `*0.95`-Pitch/Bank-Rückstellung bei `!isMoving` nur bei `!= IDLE` (sonst läuft der Zielpitch gegen 0, Gleichgewicht ≈ 37%).
- **Feuersperre (Firing-Block):** `canFire` wird VOR allen Effekten geprüft: LOS + `ObjectOnLOS2` entlang des 8-Sektor-Gewehrstrahls (Joint 8 als Mündung, Pose-Pitch + 8°, lokale -Z). Sound, Flash-MeshBit, Licht, Hülse, Rauch stehen alle in `if (canFire)`; Treffer-Logik (Static-Zerbrechen / Lara-Schaden / Funken) nur in `if (hasHit)`. Der alte Wand-Decal-Zweig ist entfernt → Wand davor oder Lara außerhalb der Schusslinie = Heli feuert überhaupt nicht.
- Weltereinheiten: `BLOCK(x)=1024*x`, `CLICK(x)=256*x` (1 Block = 4 Klicks), `SECTOR_SIZE=1024` lokal definiert.
- **Kollisions-Check (neuer Stand):** `CheckFootprintCollision(item, displacement)` – richtungs-unabhängig: 4 Yaw-rotierte Bounding-Box-Ecken (lokal −Z = Forward, aus `forwardVec = (-sinθ,0,-cosθ)` abgeleitet; `GameBoundingBox::operator+` rotiert NICHT → Ecken manuell mit `worldX = lx·cosθ + lz·sinθ`, `worldZ = -lx·sinθ + lz·cosθ`) werden um `displacement` (auch Y!) verschoben und gegen (a) `pointColl.IsWall()`, (b) exakte Durchdringung `floorHeight < Band-Unten` / `ceilingHeight > Band-Oben` (mit `NO_HEIGHT`-Guard), (c) Clearance `abs(Ceiling-Floor) <= bandHeight` geprüft. **WICHTIG: `BLOCKABLE`-Pathfinding-Box-Check NICHT verwenden** – das ist ein Begehbarkeits-Konzept (Walkability) für Laufkreaturen, falsch für einen FLIEGENDEN Heli (blockiert niedrige 1-Square-Schritte, die der Heli überfliegen kann). Ersetzt die alten `CheckEarlyBlocking`/`CheckForwardCollision`. In `ControlGunShip`: `moveDir` = Richtung (FOLLOW zum Ziel / EVADE weg, normalisiert); **Probe-Distanz = `currentSpeed`** (NICHT fix `SECTOR_SIZE` – EVADE fliegt mit `MAX_MOVE_SPEED * 2.5f` >1 Sektor/Frame und würde einen 1-Sektor-Probe tunneln); hart `×currentSpeed` → `blocked`, weich `×2·currentSpeed` → `currentSpeed *= 0.5f`.
- **Anti-Wand-Eindringen (EVADE-Satelliten-Bug):** (1) 32-Unit-Rückdruck bei Blockade NUR in `FOLLOW` + nur wenn `CheckFootprintCollision(escapeDir * 32)` frei – in `EVADE_NEAR` bleibt der Heli stehen (IDLE + Recheck), weil der Escape-Vektor dort IN die blockierende Wand zeigen würde. (2) Vertikaler Schritt `yDelta` wird vor Anwendung mit `CheckFootprintCollision(item, Vector3(0, yDelta, 0))` geprüft → bei Kollision `yDelta = 0` (kein Clipping durch seitliche Wände/Erhöhungen).
- **EVADE-Ausweichbewegung (neu):** **vorrangig rückwärts** (`moveDir` = Richtung zum Ziel, in `EVADE_NEAR` negiert → geradliniger Rückzug). **Nur bei Blockade** Kaskade: Stage 1 = lateral (Orbit um Lara – durch sich drehende Radiale eine weiche, kontinuierliche Umlaufrichtung), Stage 2 = Overfly (drüberfliegen). `GunShipOrbit.Direction` (+1/-1) hält die Umlaufrichtung über Frames stabil (kein Hin-/Her-Kippen); wird in der Kaskade je nach gewählter Laterale gesetzt. **Persistenz:** `static GunShipOrbitData GunShipOrbit` (Direction/Initialized) nach `enum GunShipState` – NICHT im Savegame (Pattern wie `Willard.cpp`); `ItemFlags` sind voll (0–7) → neuer, nicht-persistenter Zustand als statische Struktur. **`SweptFootprintClear(item, displacement)`** (nach `CheckFootprintCollision`): prüft den Fussabdruck entlang des kompletten x+y+z-Pfades in Sub-Schritten à max. `SECTOR/4` (je `CheckFootprintCollision`) → kein Wand-Tunneling/Clippen; `true` = frei. Finale Validierung nach Kaskade: `if (isMoving && !blocked && !SweptFootprintClear(*item, moveDir * currentSpeed)) blocked = true;` (fixt Overfly-Durchflug: Kaskade wählte niedrige Laterale in die blockierende Wand).
- **Tipp:** `heliFrame.BoundingBox.X1/X2/Z1/Z2` sind `const int` → bei Brace-Initialisierung als `int`-Array deklarieren (sonst C4838 Narrowing-Error). Yaw-Rotations-Mathematik mit `yawCos`/`yawSin` (float) läuft im Loop.
- **Gunship Runtime-State: EINE Struktur `GunshipData` (wichtig, ersetzt 3 alte Structs):** Die früheren 3 `static`-Strukturen `GunShipOrbitData GunShipOrbit` / `GunShipEscapeData GunShipEscape` / `GunShipLosData GunShipLos` sind zu EINER `struct GunshipData` (Instanz `static GunshipData GunShip;`, lokal nach `enum GunShipState`) zusammengeführt. Member (Namen unverändert, keine Kollisionen): `Direction`/`Initialized` (Orbit), `Active`/`TargetPos`/`Frames` (Escape), `LastTestFrame`/`Clear` (LOS-Cache). `Reset()` → **`ResetEscape()`**. Aufrufe jetzt: `GunShip.Direction`, `GunShip.Active`, `GunShip.TargetPos`, `GunShip.Frames`, `GunShip.LastTestFrame`, `GunShip.Clear`, `GunShip.ResetEscape()`. **Vorherige Notizen mit `GunShipOrbit.*`/`GunShipEscape.*`/`GunShipLos.*` meinen denselben Zustand → `GunShip.*`.** Nicht-persistent wie zuvor.
- **Lara im Wasser erkennen (wiederverwendbar, für KI/Vehicle-Logik):** Globaler `Lara` (`extern LaraInfo Lara;`, lara.h) + `Lara.Control.WaterStatus` (Enum `WaterStatus`: `Dry`=an Land, `Wade`=watscheln, `TreadWater`=Oberfläche, `Underwater`=taucht/unter Wasser, `FlyCheat`, lara_struct.h). `tr3_scuba_diver.cpp`-Idiom: `== WaterStatus::Dry` = an Land. **Gunship:** `ControlGunShip` setzt bei `engaging`(FOLLOW/IDLE) + `Lara.Control.WaterStatus == WaterStatus::Underwater` → `IDLE` (Heli hält, solange Lara taucht; release bei Auftauchen/TreadWater oder an Land; ESCAPE/EVADE unangetastet). **Zusätzlich Y-Achse:** Im IDLE-Zweig `ySpeedTargetIdle=0` bei `Underwater` → Heli hält seine Höhe, sinkt der tauchenden Lara nicht nach (Y-Bewegung läuft nur über `currentYSpeed`→`yDelta`, keine Schwerkraft).
- **Gunship Flight-Steering (Refactor, ersetzt den EVADE-Cascade-Stand):** (a) `ResolveProbeRoom(pos, startRoom)` = Probe liegt in aktuellem Raum ODER verbundener Nachbarraum (`IsPointInRoom` + `RoomData::NeighborRoomNumbers`), sonst `NO_VALUE`. **Das** ist der verlässliche Check für „in gültiger verbundener Room-Geometrie, nicht im Horizon“ – `GetPointCollision`/`GetRoomVector` clamped bei Void-Punkten auf den aktuellen Room und sind dafür NICHT verlässlich. (b) `CheckFootprintCollision` prüft JEDER der 4 Bounding-Box-Ecken erst `ResolveProbeRoom` (`NO_VALUE` → Kollision) dann Wand/Floor/Ceiling/Clearance → fixt Portal-Traversal + zu schmale Portale + Horizon-Flug, behält echte Modell-Bounds. (c) `FindBestAvoidanceDirection(item, preferredDir, probeDist, outDir)`: 5 Kandidaten (0/±45/±90°) um Preferred-Richtung (2D-Yaw-Rotation), je `SweptFootprintClear`, Scoring = kleinster Winkelabstand + Continuity-Bias auf `GunShipOrbit.Direction`. (d) **Unified Steering** gilt für FOLLOW/MoveTo UND EVADE: Preferred → `FindBestAvoidanceDirection` → Overfly (vertikal, nur Decken-Clearance) → `blocked`(Hover); Collision-Vermeidung > Combat-Distanz. (e) **FOLLOW-Bewegung nutzt `moveDir`** (davor eigene Ziel-Zuformel); **finale Validierung ist Overfly-aware** (`moveDir*speed` + `-EVADE_OVERFLY_HEIGHT`). (f) `#include "Game/room.h"` nötig für `IsPointInRoom`/`NeighborRoomNumbers`.
- **Gunship Fußabdruck = Gitter, nicht nur Ecken (wichtig):** `CheckFootprintCollision` nutzt ein **4×4-Raster (16 Stichproben, `FOOTPRINT_GRID=4`) über die gesamte Bounding-Box-Fläche** (Ecken, Kantenmitten, Innenpunkte), NICHT nur die 4 Ecken. Grund: ein großer (6–7 Sektor) Fußabdruck verfehlt mit 4 Ecken Wände, die zwischen Zentrum und Kante liegen („Heli fliegt durch Wände" – vor allem bei Rückwärtsflucht/EVADE). Jeder Gitterpunkt: `ResolveProbeRoom` → `GetPointCollision` (Wand/Floor/Ceiling/Clearance). Gitter = strikter als 4 Ecken, aber keine Fehl-Positiven (alle Punkte liegen im echten Modell-Bereich).
- **Gunship Auto-Escape (nicht-persistent, via MoveTarget):** Bei Blockade in `EVADE_NEAR` **ODER `ESCAPE`** (Wand/Roombound) + Shoot-Target → `FindEscapeTarget` wählt den nächsten gültigen Punkt (Ring aus 12 Kandidaten im Umkreis des Shoot-Targets, horizontal, auf Heli-Höhe, Mindest-Fluchtdistanz `2 * SECTOR_SIZE` vom Heli), der **≥ Shoot-Reichweite** entfernt ist und **Flug-Clearance in verbundenen Räumen** bietet (Destination + Pfad-Punkte `disp*0.33/0.66/0.9` per `CheckFootprintCollision` — nur die Pfad-Mitte würde Blockaden im letzten Stück vor dem Ziel verpassen). Gespeichert in `static GunShipEscapeData GunShipEscape` (`Active`/`TargetPos`/`Reset`, nach `GunShipOrbit`). **Ausschluss (Stuck-Loop-Fix):** `FindEscapeTarget` nimmt `excludePos`/`excludeRadius` (`ESCAPE_EXCLUDE_RADIUS = 2 * SECTOR_SIZE`, XZ-Abstand); Aufruf gibt das bisherige `GunShipEscape.TargetPos` als `excludePos` → das zuletzt fehlgeschlagene Ziel wird bei der Neu-Suche NICHT erneut gewählt (Trigger feuert auch WÄHREND ESCAPE → kein deterministischer Endlos-Loop mehr). `GunShipEscape.Frames = 0` bei jedem neuen Target (frisches Timeout-Fenster). **Wiederverwendung der MoveTarget-Pipeline:** Top von `ControlGunShip` setzt bei `Active` `moveTargetPos`/`hasMoveTargetPos`; `DetermineGunShipState(hasMoveTargetPos=true)` → `ESCAPE`-State → Heli fliegt zum Escapetarget (da `hasMoveTargetPos` vor `EVADE_NEAR` geprüft wird, Vorrang vor Combat-Distanz). **One-Shot-Block** (Erreichen < `MOVE_TARGET_REACH_RADIUS`) ruft `GunShipEscape.Reset()` auf → Kampf wird fortgesetzt. **Feuersperre:** `hasShootTargetInRange` enthält `&& !hasMoveTargetPos` → Heli feuert NICHT auf das Shoot-Target, während er zum Escapetarget fliegt.
- **Gunship MoveTarget/Escape: One-Shot-Clear MUSS horizontal sein (wichtig):** Im `FOLLOW` schwebt der Heli IMMER `HOVER_HEIGHT_OFFSET` (1,5 Sektoren ≈ 1536 units) UNTER dem Ziel (`idleTargetY = targetPosIdle.y - HOVER_HEIGHT_OFFSET`, tr5_gunship.cpp). Deshalb: `DetermineGunShipState` entscheidet mit **horizontaler** Distanz (`horizontalDistance < 100` → IDLE), und der **One-Shot-Clear darf NUR die horizontale Distanz** (`dmx²+dmz²` < `MOVE_TARGET_REACH_RADIUS`) prüfen. Bei 3D-Distanz (`dmx²+dmy²+dmz²`) erreicht der Heli wegen der vertikalen Offset nie < Radius → State (Escape/MoveTarget) wird nie geklärt → Heli steckt in IDLE fest und (wegen Feuersperre) feuert nicht. **Sicherheitsnetz:** `GunShipEscapeData.Frames` + `MAX_ESCAPE_FRAMES`(240) leert den Escape-Zustand, falls das Ziel (z.B. durch blockierten Pfad) nicht rechtzeitig erreicht wird → Kampf/Firing wird fortgesetzt.
- **Gunship Escape-Anflug: Nase auf LARA + waagerechter Flug (wichtig, aus Test abgeleitet):**
  - **Nase:** WÄHREND des Escape auf **Lara** zeigen (nicht auf das Escapetarget)! `targetOrient`-Bedingung bleibt `if (hasShootTarget && shootTargetNum >= 0)` (KEIN `!hasMoveTargetPos`). Test-Ergebnis: Nase→Flugziel sah SCHLECHTER aus („am Seil hochgezogen") als Nase→Lara → Nase→Lara beibehalten.
  - **Waagerecht fliegen:** Im `FOLLOW` bei `hasMoveTargetPos` auf **Ziel-Höhe** fliegen (`idleTargetY = moveTargetPos.y`), KEINE `HOVER_HEIGHT_OFFSET`. Sonst steigt/fällt der Heli langsam (Hover-Offset + langsamer Y-Lerp `yLerpAlpha=1/16`) → wirkt wie „am Seil langsam hochgezogen". Waagerechter Flug = natürlicher Anflug.
  - **Bekanntes Residuum:** Heli bleibt in engen Stellen ggf. hängen („nicht vorhandene Items" = False-Positive vom 4x4-Grid + `ResolveProbeRoom`). Falls anhaltend: Grid kleiner (3x3). - **Gunship ESCAPE-State (wichtig):** Der Escape-Flug hat einen eigenen `GunShipState::ESCAPE` (=3), nicht FOLLOW-Reuse. `DetermineGunShipState`: `hasMoveTargetPos` → `ESCAPE`. **Bug-Fix (Stuck):** Evade-Flag (`ItemFlags[7]`) wurde beim Escape-Trigger NICHT zurückgesetzt → `if (ItemFlags[7]==1) currentState=EVADE_NEAR` zwang den State auf EVADE_NEAR → Heli steckte im EVADE-Loop (bewegte sich nicht). - **Gunship FOLLOW-Wand-Logik (wichtig, neu):** `FOLLOW` (Vorwärtsflug) nutzt **nur System 1** (`blockedEarly` = `CheckFootprintCollision(*item, dirToTarget * SECTOR_SIZE)`, 1 Sektor in Zielrichtung) — die **Ausweich-Kaskade** (`SweptFootprintClear` + `FindBestAvoidanceDirection` + Overfly) und die **finale Validierung** (`SweptFootprintClear(moveDir * currentSpeed)`) laufen **NUR in `EVADE_NEAR`/`ESCAPE`** (Gates `currentState != GunShipState::FOLLOW` an Kaskade + finale Validierung). **Folge:** FOLLOW + Wand → `DetermineGunShipState` liefert IDLE (kein Vorwärtsflug, keine laterale Ausweichbewegung, kein Overfly, kein Tunneling da 64 < 1024 Units/Frame). IDLE + Wand → bleibt IDLE. **Stateless:** `blockedEarly`/`blocked` sind pro-Frame-lokal (neu aus Geometrie), kein Reset nötig. **FOLLOW-Rückdruck entfernt** (war tot, da `blocked` in FOLLOW nach Gates nie true). `EVADE_NEAR`/`ESCAPE` unverändert (inkl. Fluchtroute via `FindEscapeTarget`).
- **Gunship ESCAPE-Stuck-Root-Cause (wichtig):** Die Bewegungs-Geschwindigkeit war über `currentSpeed = targetSpeed * pitchRatio` AM PITCH gekoppelt (`pitchRatio = |currentPitch|/maxPitch`; `currentPitch` aus `ItemFlags[1]`; `isMoving = currentSpeed > 1.0`). Ein frisch getriggter ESCAPE (Austritt aus blockiertem/„pitch-null"-State) hat Pitch ~0 → `currentSpeed~0` → `isMoving=false` → **keine Bewegung**; der Pitch-Ramp (Lerp-Alpha `1/powf(2, PITCH_LERP_SPEED=5)` = 1/32 pro Frame) wird zusätzlich von (a) Inertie (erste `INERTIA_FRAMES=25` Frames: `targetSpeed*=0.15`) und (b) `!isMoving`-Dämpfung (`currentPitch*=0.95` pro Frame) unterdrückt → Heli crawlt/steht still (Symptom: ESCAPE-Ziel = weiße Kugel sichtbar, Heli bewegt sich nicht). **Fix (aktuell ESCAPE-only):** `float currentSpeed = (currentState == GunShipState::ESCAPE) ? targetSpeed : targetSpeed * pitchRatio;` → ESCAPE fliegt mit voller `targetSpeed` (MAX_MOVE_SPEED=64), unabhängig vom Pitch; `isMoving` immer true → Dämpfung greift nie. **Anmerkung (FOLLOW-Test, aktueller Stand):** Die FOLLOW-Pitch-Entkopplung wurde WIEDER rückgängig gemacht (war laut Nutzer nicht der Fehler) – FOLLOW behält die „Lean=Speed"-Kopplung. Zudem ist der FOLLOW-Wand-Check `blockedEarly` testweise deaktiviert (immer `false`, `dirToTarget`-Block entfernt) → Heli fliegt im FOLLOW-Zweig jetzt auch durch Wände (bewusst, für den Test). Ausweich-Kaskade + `if (blocked)`-Block + Y-Position-Prüfung bleiben erhalten (alle nur für ESCAPE/EVADE_NEAR aktiv via `currentState != FOLLOW`). **Merke:** „Lean=Speed" ist für ESCAPE kontraproduktiv – Notfall-Ausflüge brauchen pitch-unabhängig volle Geschwindigkeit.

- **Gunship ESCAPE/EVADE_NEAR-Stuck-Loop (wichtig, neu):** Der Auto-Escape-Trigger im `blocked`-Zweig feuerte `FindEscapeTarget` bei `blockedState == EVADE_NEAR || ESCAPE`. Bei Blockade (Escapetarget zu nah an Wand) wurde das Ziel **jedes Frame neu gewählt** + `GunShipEscape.Frames=0` → Timeout (280) lief nie aus, One-Shot (Reach 512) nie erreicht → `GunShipEscape.Active` pendelte false→true→false pro Frame → Heli kippte zwischen EVADE_NEAR und ESCAPE hin und her **ohne Bewegung** (Symptom: weiße Kugel sichtbar, Heli steht still). **Fix:** Trigger-Condition auf `blockedState == GunShipState::EVADE_NEAR` reduziert → im ESCAPE-Flug bleibt der Heli am aktuellen Escapetarget **verpflichtet** (bis Erreichen/Timeout) und tauscht es nicht permanent aus. **Merke:** Escape nur aus EVADE_NEAR (Initiating-State) neu lösen, NICHT aus ESCAPE (Committed-State) – sonst Ziel-Ping-Pong. **Separat:** „keine Bewegung" kann auch durch blockierten Pfad (Wand/Decke, `SweptFootprintClear`/Kaskade → `blocked`) kommen – dann Wand-Check testweise deaktivieren (wie FOLLOW) oder freies Escapetarget wählen.
- **Gunship ESCAPE-Standstill (wichtig, neu):** ESCAPE-Steuerung lief durch die Ausweich-Kaskade; in engen Spalten (Wände links/rechts/hinten) waren Preferred + alle 5 Ausweich-Kandidaten + Overfly-Punkt (1 Sektor voraus + 3 Sektoren hoch) blockiert → `blocked=true` → Heli stand still (Auto-Escape feuert nur aus EVADE_NEAR → kein neues Ziel → Standstill bis 280-Frame-Timeout). **Fix:** Ausweich-Kaskade + finale Validierung NUR für `EVADE_NEAR` (Gates `currentState != FOLLOW && currentState != ESCAPE`); ESCAPE = gerader, verpflichtender Notflug zum (in `FindEscapeTarget` validierten) Escapetarget, notfalls durch Geometrie (Test-Modus wie FOLLOW). **Prinzip:** ESCAPE = committed flight (Kaskade aus), EVADE_NEAR = combat orbit (Kaskade an). Debug-Kugel (`DrawDebugSphere`) jetzt auf Top-Ebene → sichtbar solange `GunShipEscape` aktiv (auch während des Flugs).
